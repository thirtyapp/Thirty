O-3 (policy edge, executed). On slow storage, the user taps Start, then pauses the Plan, then closes the Circle:
- The Start is only recorded once its save lands, so the Pause counts as coming first.
- Result: the Circle runs and closes, and earns no credit.

This follows the letter of "Pause before a valid Start earns no credit" under decision B, but not the order the user tapped. The founder should confirm this is intended.

5. New findings

AUD-N1 — MEDIUM — R8.2 regression — a stale "started after expiry" flag withholds a credit the user is owed after a restart

- Where:
  - lib/features/plans/domain/circle_plan.dart:727–733: toJson copies the whole stored record (...?source) and only ever adds startedAfterExpiry: true.
  - noteStart (:1211–1227) flips the flag from true to false in memory.
  - The false value is never written: disk keeps true.
- This contradicts:
  - the founder rule "credited if served and started under Premium";
  - LIMITATIONS_R8_2.md item 5: "the next Start rewrites it";
  - the R81-A05 claim that only the fields THIRTY sets are changed.
- Reproduced (audit_r82_adversarial_test.dart):
  a. The user starts a stage Circle after a verified expiry.
  b. The process stops right after the Plans note lands. (Decision B writes that note first; I simulated the stop with the harness's stopAfter.)
  c. The user restarts and resubscribes, then starts the Circle under verified Premium. In memory creditsServed is true, but disk still says startedAfterExpiry: true.
  d. Premium lapses, the app restarts, and the user closes the Circle. Credits on disk: 0 (expected 1).
- Controls:
  - The same sequence without the final restart is credited (1).
  - The domain-level test passes on R8.1 (e935112c) and fails on R8.2, which proves R8.2 introduced it.
- Impact: credit withheld, never wrongly granted. Whether the user gets the credit depends on whether the app restarted. The trigger is rare.

AUD-N2 — LOW — R8.2 regression — a deleted session's Start time is written back after Delete

- Where:
  - CirclePlansNotifier._startedAt and _closeRequestedAt (circle_plans_provider.dart:309–317) are never cleared, including by forgetStageEvidence (:895–924).
  - Circle ids are day keys, so a stage Circle served again on the same day after Delete gets the same id.
  - _withActionOrder (:335–380) then uses the deleted session's time.
- Reproduced:
  a. Start a stage Circle at 09:00.
  b. Delete Circle history; it succeeds, and History and the day keys are gone.
  c. The same stage Circle is served again for the same day.
  d. Pause the Plan before starting it. Disk now holds lastServed.startedBeforePause: "2026-10-12T07:00:00.000Z", the deleted session's Start.
- The Leave/Close variant follows the same code path (static analysis, not run).
- Impact:
  - It breaks the Delete contract (today's session is deleted) with one timestamp that persists until the next served Circle or the next Delete.
  - It grants no wrong credit, because the time can never match a later Start.
  - On R8.1 the field did not exist (the test passes there).

AUD-N3 — LOW — pre-existing since R8.1 — Delete saves a Plan change that was reported as not saved

- Where: circle_history_deletion.dart:180 calls forgetStageEvidence() without first waiting for the Plans queue. That clears _queued, so when the earlier failing write is refused, its rollback is skipped. Delete then writes the optimistic state.
- Reproduced on both R8.2 and R8.1:
  a. Hold the Plans write for a Pause.
  b. Start Delete.
  c. Release the held write as a failure.
  - Result: the user is told the save failed (last=circlePlans), yet disk says paused, and unsaved stays set.
- Impact: a false failure notice; no data is lost and nothing false is confirmed.

Observations (not blocking)

- O-1 (static). Delete keeps the new ElementLeftOut.byInsight ids in Suggestion Preferences. These ids encode the Insight family, date and part of a deleted Insight. Minor residue; the founder should decide.
- O-2 (static, not run). analyticsConsentKey, the tester id and cohort keys, and firstBreathLastPlayedDateKey still use typed getters. A wrong native type would throw on read. This is outside A09's stated scope.
- O-3: see §4.
- Hypothesis disproven by execution: a Start waiting for its save is not silently dropped when the app resumes (AUD-N4 passed).

8. Persistence, recovery and deletion

Native write behaviour. shared_preferences_android 2.4.27's legacy plugin, which SharedPreferences.getInstance uses, calls commit() (LegacySharedPreferencesPlugin.kt:53–101). So on Android, writeConfirmed returning true means the platform has committed the write to its file. This is from reading source only.

Memory-held action order is acceptable. The Start/Close order is saved atomically inside the Pause or Leave save. If the process dies before that save, there is nothing to order. If the Close is not durable, the user closes again later, and that Close earns no credit, as the policy says. I found no case where a process kill grants a wrong credit.

Two restart risks remain:
- AUD-N1 is a restart-dependent divergence between memory and disk.
- A kill between the platform commit and Dart's confirmation (an untested risk, not an observed defect) is safe for Plans and Today, because they re-read the disk on start.

Deletion. R81-A02 and NEW-2 are closed. AUD-N2 (new) and AUD-N3 (old) remain.

Malformed and future-schema data. Preserved, except the AUD-N1 write-back defect.
