4. New findings

NEW-1 — MEDIUM, blocks baseline acceptance — R8.1 regression: a stage Circle becomes permanently unsaveable once lastServed no longer matches it

Root cause:
- _publish now requires confirmServed for any stage Circle on show (recommendation_provider.dart:833–840).
- confirmServed throws StorageWriteFailed unless the Plans' single lastServed slot still matches that Circle (circle_plans_provider.dart:272–284).
- _persist calls _publish before _recordInJournal (:2385–2416), so neither the day keys nor History receive the Start, Close or answers.
- Nothing ever restores lastServed. _newCycle (circle_plan.dart:767–781) builds a PlanProgress without it, and both start on a left or ended Plan (:786) and goThroughAgain (:831) go through _newCycle.

Trigger A — no storage fault. The user finishes stage 5, so the Plan ends. They tap "Go through it again" on the review page (plan_detail_page.dart:367–376), or apply the I1 Insight (insights_provider.dart:300–305). Then they answer that Circle's reflection.
- Leaving and then starting the Plan again mid-Circle (plan_actions.dart:36–39, :90) has the same effect on the Close itself.

Trigger B — one transient Plans failure at choice time. The served write fails once and the Plans roll back. The Circle stays on screen; the user can still Start, run, Close and answer it, and none of it is saved.

What I observed:

Why it matters:
- Explicit user answers, or a Close, are lost on healthy storage in a normal flow.
- Retrying can't help.
- The notice dedupes per Circle (_told, journal_save_failure_notice.dart:98–115), so every refusal after the first one is silent.

The accepted limitation understates this. "Pending-then-failed stage Circle stays visible … never saved" does not say that:
- a single transient failure is enough;
- the user can still run and close the whole Circle;
- History then loses all of it.

Test gap: no R8.1 test runs a stage Circle through any Plan lifecycle action. The B8 simulation runs "Go through again" only when endedOn != today (b8_product_simulation_test.dart:228–233), which avoids exactly this path.

Acceptance condition:
- A stage Circle whose served record was once confirmed must stay publishable after a Plan action. For example, Today could remember that confirmation the way it keeps _startVerdicts, or the new-cycle actions could keep lastServed.
- A Circle that can't be confirmed must either be saved without stage credit or be refused at Start. It must never be silently run and then lost.
- Plus a regression test for both triggers.

NEW-2 — LOW — After a failed Delete, a later failed Plans or Insights save brings deleted evidence back in memory

- forgetStageEvidence and forgetAll advance _durable only when they succeed (circle_plans_provider.dart:511, insights_provider.dart:433). The RL-1 rollback (:200, :139) therefore goes back to the pre-deletion state.
- Reproduced (throws and returns false):
  - Delete fails, so memory holds 0 stage records.
  - A later unrelated save fails: memory holds 1 record again.
  - After the store heals, the next save writes that state.
  - The deletion intent stays on disk, and restart removes the record (0 on disk, 0 in memory).
- Impact: limited to that session, but it is user-deleted data shown and re-saved. R8 didn't revert memory.

NEW-3 — LOW — confirmed() can report notSaved for a change that is on disk

- ensureSaved returns the action's own write. If that write fails while a later queued save carrying the same change lands, the rollback is skipped (latest is false) and the change is durable, yet notSaved is returned.
- Reproduced: the store is told it failed, the gentler setting is on disk, and the result is notSaved.
- Related observation (not a finding): if only the I1, I2 or I3 applied mark fails, a retry returns alreadyApplied without marking. Only I4 retries the mark. The Insight then goes stale rather than showing as applied; the change itself stands.

E-1 — LOW (evidence tooling) — run_batches.py report doesn't detect a missing partial batch

- With batch_17c.summary.json removed, report printed EVIDENCE OK with 2,596 tests, exit 0 (run_batches.py:185–236 checks coverage by file, not by test count).
- cases does catch it (exit 1). Both commands must be run.
- The committed evidence itself is complete.

8. Durable data integrity

Sound:
- Plans and Insights rollback with several saves queued: each save writes the whole record, and only the latest failure reverts.
- ensureSaved deduplication.
- Credit across a lapse together with a failed Start.
- Removing an answer, then recovery, then the next day's choice.
- Preservation copies racing a successful Delete.
- Lossless write-back of malformed and future-schema data.
- Wording of damaged kept Circles.
- Midnight, the six-hour carry-over, both 02:30s of the DST night, and no-touch provenance.
- Failure notices when several stores fail (counted, one follow-up).

Weak:
- The new stage-Circle gate (NEW-1);
- rollback after a failed Delete (NEW-2).

Deliberate: Delete also drops unreadable Plans and Plan-level unknown fields, as possible evidence. That is consistent with what Delete promises.
