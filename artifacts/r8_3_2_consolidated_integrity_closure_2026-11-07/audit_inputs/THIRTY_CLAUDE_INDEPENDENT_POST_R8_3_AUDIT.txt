5. R83-F1 — HISTORICAL CREDIT
The single slot holds as far as day keys go. A new Circle can be served and started only after _recordBeforeOverwrite has resolved the previous day's session, and _withEarnedCredits only reads lastServed. So overwriting the slot never re-exposes an earlier Circle; I found no failing scenario for slot capacity.

It fails in three other places:

AUD-R83-1 — MEDIUM — DEMONSTRATED, no fault injection. This is pre-existing (it fails on R8.2 too), so the R8.3.1 fix is incomplete.
- Sequences: Pause → Start → Close → Resume → Leave → Go through it again → restart (or next day); also Pause → Start → Resume → Close → Leave → Again.
- Result: 0 credits in the session, 1 after the restart. The left cycle #1 gets a stage-1 guided record and its cursor moves to 2. It also reproduces after a verified lapse and resubscription.
- Mechanism:
  1. Leave from an active Plan stamps closedBeforeLeave (_withActionOrder, circle_plans_provider.dart ~342–380), because the uncredited Circle is not skipped.
  2. _newCycle (circle_plan.dart ~962–983) carries lastServed when closedBeforeLeave != null, but builds PlanProgress without startedWhilePaused.
  3. On the restart or next day, _mirrorInJournal or _recordBeforeOverwrite calls recordGuided. With the slot gone, the left-cycle branch needs only closedFirst (circle_plan.dart ~1176–1186), so the Circle is credited.
- Contrary to: founder rows "Pause → Start → Close → Resume" and "Pause → Start → Resume → Close" (no credit), and "a later lifecycle change never makes an ineligible Start eligible".
- No R8.3 test covers Leave + Go through again for a paused Start.
- By static reading only (not executed), start() on a left Plan and the I1 goThroughAgain share the same path.

AUD-R83-2 — LOW — DEMONSTRATED with a refused Plans write. Pre-existing class.
- Sequence: Plan durably paused. Resume, with its write still pending, and Start tapped meanwhile. The Start takes the fast path: noteStartedWhilePaused sees the Plan as active, so no slot is written.
- The store then refuses the Resume. The Plan goes back to paused, the user is told, and the Circle keeps running.
- Close: 0 credits. A later successful Resume and a restart: 1 credit.
- The valid Start happened while the Plan was durably paused, and per RL-1 a refused change never happened.

AUD-R83-3 — LOW — DEMONSTRATED. A REGRESSION introduced by R8.3.1: the same test passes on R8.2.
- Sequence: Pause, then Start. The slot write lands, then the Start's own day-keys save fails. After a restart the Circle is not started, but startedWhilePaused stays on disk.
- Then Resume → Start on the active Plan → Close: 0 credits. Expected 1: the only durable Start was made on an active Plan.
- The cause: the slot is written before the Start is durable, and nothing removes it when the Start never becomes durable.

Controls that pass (executed): all founder-table rows; Start → Pause → Close credited once; Delete removes the slot; same-day re-serve after Delete is credited once; Delete during the slot write leaves no residue.

The ack-lost variant on the slot write did not reproduce a stale slot.

10. L-1 — OPEN — PRE-RELEASE BLOCKER (not fixed, not waived)
- Confirmed by source reading: Delete reports success while a wholly unreadable Preferences record keeps byInsight, and Export omits that record.
- It does not affect any decision in this build: the record reads as empty and is never applied.
- The privacy consequence is real but narrow: History-derived evidence (which Insight caused a choice) survives a Delete that the user was told succeeded, and the user cannot see or export it.
- No existing build produces such a record. It arises only from a downgrade, a restore or outside damage.
- The documented scope and severity are accurate.
- It does not block the engineering baseline, but it does block commercial release.
- Safe remediation: L1_ASSESSMENT options 1+2. Delete finishes everything else and then tells the user truthfully that the preferences couldn't be checked and Reset clears them; Export carries the record exactly as stored. Never mutate or delete the unknown record automatically. Any future schema change must define downgrade behaviour.
- Fresh Delete races checked:
  - pending Plans writes (landed, refused);
  - pending Preferences writes;
  - a refused attribution removal;
  - stopping after the intent;
  - same-day re-serve;
  - the slot write in flight.
  None regresses; one hypothesis remains (H1).
